# V2 弱去中心化多 Agent 协作引擎：项目需求与实现方案

> 版本：v1.0 ｜ 日期：2026-08-24 ｜ 状态：待自我审查 + 圆桌评审
> 仓库：https://github.com/silicon-sbt/agent-roundtable-mcp（单一仓库，V2 在现有代码上演进）

## 1. 背景与定位

现有 agent-roundtable-mcp 提供 **V1 圆桌会议**（模式 A）：LangGraph 状态机内多 Persona 轮流发言、主持人引导、产出评审结论。它本质是**审议型**工具——"合理性审查会议"。

本方案定义 **V2 弱去中心化多 Agent 协作引擎**：在保留 V1 会议能力（模式 A）的基础上，新增**协作执行**能力（模式 B）——主 Agent 分派任务给多个子 Agent，子 Agent 在执行过程中通过**定向横向通道**互相交流（指名回应、引用、受监督的小组同步）。V2 是 V1 的超集：**公司也会开会**，模式 A 是模式 B 的对齐/评审机制。

### 1.1 核心设计原则

1. **star 骨架 + 弱去中心化**：主 Agent（经理/主持人）保留调度、分派、裁决、汇总权；子 Agent 之间开放定向交流通道，所有横向交流在主 Agent 视野内可仲裁。
2. **会议是子能力**：V1 圆桌保留为模式 A，可被模式 B 按需召集（对齐、评审、决策）。
3. **向后兼容**：MCP 工具名与现有注册（DSH/Claude Code）不变，V1 行为默认保留。

## 2. 目标与非目标

### 2.1 目标

- G1：主 Agent 能创建并分派任务给多个子 Agent（带输入、期望产出、依赖关系）。
- G2：子 Agent 在执行中能**指名回应/引用/同步**另一位子 Agent（弱去中心化通道）。
- G3：主 Agent 能按需召集模式 A（圆桌会议）对齐或评审。
- G4：子 Agent 拥有**跨会话持久记忆**（按策略注入，避免全量历史）。
- G5：全程可观测、可干预、可回滚；成果沉淀为报告。
- G6：对外仍是同一套 MCP 服务（DSH / Claude Code 已注册配置零迁移）。

### 2.2 非目标

- 不做完全 mesh（人人平等自由对话，无中心裁决）。
- 不做外部 MCP 消息总线 / 跨进程自治 Agent 网络（留观察项）。
- 不引入第二套运行时（不采用 AutoGen/CrewAI 框架锁定）。
- 不做子 Agent 自主拉起其他 Agent 的递归授权（控制复杂度）。

## 3. 使用场景

### 场景 1：跨领域调研协作（模式 B）
主 Agent 分派三个子 Agent 分别调研「技术可行性」「市场规模」「合规风险」，设定互相可引用的范围；子 Agent 调研中发现的技术约束直接同步给市场子 Agent，合规子 Agent 引用前两者产出给出风险清单；主 Agent 最后召集模式 A 圆桌评审结论。

### 场景 2：方案设计评审（模式 A，V1 现状）
主 Agent 召集多专家圆桌对设计方案表态、互相反驳、形成共识——V1 能力，V2 保留并可选启用记忆。

### 场景 3：代码评审协作（模式 B + A）
主 Agent 分派「架构审查」「安全审查」「性能审查」三个子 Agent 并行检查同一 PR；安全子 Agent 发现的问题指名同步给架构子 Agent 确认影响面；完成后召集圆桌汇总评审结论。

## 5. 非功能需求

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| NFR1 | Token 成本上限 | **双层预算**：每任务配额（默认 ≤80k）+ 全局熔断（默认 ≤400k）；超限自动终止该任务或整场并给部分总结；记忆用摘要/检索注入避免平方级膨胀 |
| NFR2 | 并发与幂等 | MCP 工具重入去重（同 request id 不重复执行）；Checkpointer 写入用事务锁 |
| NFR3 | 失败恢复 | 任一子 Agent LLM 调用失败 → 单点重试/跳过并记录；**回滚粒度为单任务级**（该任务回到上一提交点），Manager 可中止整场（已完成任务保留产出，未完成任务标记 failed/blocked） |
| NFR4 | 安全 | key 只进 .env；报告读取限制目录；工具不暴露宿主机任意文件；**记忆数据存本地（SQLite），默认不进报告/日志，除非主 Agent 显式要求** |
| NFR5 | 兼容性 | DSH schema 子集（无 anyOf）；真实 LLM 圆桌超时用 toolCallTimeoutMs + 预留异步任务轮询 |
| NFR6 | 可观测性 | 进度上报（MCP progress）、事件日志、失败详情可读 |

## 6. 架构设计

```text
┌─────────────────────────────────────────────┐
│ MCP 层（FastMCP）：run_roundtable / run_collaboration /   │
│        plan_council / manage_tasks / list_reports ...      │
└──────────────────────┬──────────────────────┘
┌──────────────────────▼──────────────────────┐
│ 编排层（LangGraph）                          │
│  Manager 节点（star 中心：分派·裁决·汇总）   │
│   ├── 模式A：会议子图（V1 保留）             │
│   └── 模式B：任务子图 × N（Send fan-out）     │
│        └── 横向通道：reply_to 指针 + 受监督小组 │
│  Checkpointer：每 Agent 持久会话（SQLite）   │
└──────────────────────┬──────────────────────┘
┌──────────────────────▼──────────────────────┐
│ 模型层：LLM client（OpenAI 兼容+重试）+ RAG  │
└─────────────────────────────────────────────┘
```

### 6.1 核心概念

- **Manager**：主 Agent 在引擎内的化身（模式 A 称主持人，模式 B 称经理），唯一拥有分派/裁决/中止权。Manager 自身上下文同样增长，采用与子 Agent 相同的摘要/检索注入策略管理。
- **Task**：分派单元（id、输入、期望产出、依赖、可见交流对象、预算）。
- **Agent 会话**：每个子 Agent 一个持久上下文（Persona + 记忆 + 任务上下文）。
- **Message**：带 `reply_to` 指针、`scope`（全员/指定对象）、认识论标签。

## 7. 实现方案（技术选型）

### 7.1 编排

- **LangGraph**（现有依赖）：Manager 节点 = supervisor；模式 B 用 `Send` API 动态 fan-out 创建任务子图；任务子图共享 reducer 收集消息。
- **发言顺序**：Send 是异步无序的 → Manager 节点显式拍板（谁先发言、谁能回应谁），保证可控收敛。

### 7.2 消息模型

- `RoundtableMessage` 扩展：`reply_to`（可选，指向消息 id）、`scope`（默认全员）、`task_id`（模式 B 归属）。
- 横向交流 = 子 Agent 的消息带 `reply_to` 且 `scope` 限定 → 由 Manager 裁决后定向投递。

### 7.3 记忆

- **Checkpointer**：langgraph-checkpoint-sqlite，按 agent 分区（每个 Agent 用独立 thread key 或独立子图 checkpointer）实现跨会话持久；注意 LangGraph Checkpointer 是 graph 级快照，须按 agent 隔离 key。
- **注入策略**：检索（基于当前话题/任务关键词取 Top-K）+ 摘要（旧记忆压缩为摘要）→ 注入 prompt；不做全量历史拼接。
- **治理**：记忆条目带时间戳/来源/置信度；Manager 可否定或过期旧记忆。

### 7.4 MCP 工具

新增（保持字符串/标量参数，DSH schema 兼容）：

- `run_collaboration`：模式 B 入口——`tasks`（JSON 字符串：任务定义数组）、`allow_links`（可交流对象矩阵）、`rounds`、`mock`、`provider` 等。
- `manage_tasks`：查询/中止任务、查看横向交流记录。
- `run_roundtable` 增加 `memory` 开关与 `reply_to` 支持（向后兼容默认关）。

### 7.5 兼容

- DSH schema 子集：所有新参数用字符串/标量（沿用 `add_personas` 的 JSON 字符串模式）。
- 超时：`toolCallTimeoutMs` 调大 + 预留异步任务轮询（`manage_tasks` 查状态）。

## 9. 验收标准

1. **功能**：任务分派/执行/横向交流闭环；指名回应准确命中；记忆跨会话召回且不泄漏；Manager 可中止/裁决。
2. **对比**：同一话题下模式 B 的"互驳率/信息复用率"高于模式 A 基线——度量定义：**信息复用率 = 引用/回应他人消息的条数 ÷ 总发言条数**；**互驳率 = 明确反驳他人观点的发言条数 ÷ 总发言条数**。
3. **失败恢复**：单点失败可跳过/重试，整场可回滚。
4. **并发幂等**：重入去重、Checkpointer 写锁。
5. **成本**：预算熔断生效，无失控场景。
6. **兼容**：DSH schema 校验通过、Claude Code 实测、V1 行为回归无破坏。

## 9.5 会议动议权（FR11）设计定稿

（2026-08-24 用户确认，第三方评审提问结论）

1. **触发条件：混合**——事件驱动为主（完成任务里程碑/发现跨领域冲突/需要输入时）+ 每任务 1 次自由裁量额度。
2. **审批：二元 + 拒绝必带原因**——经理批准或拒绝；拒绝不带原因则退回重审（保证可审计、可改进）。
3. **重试：允许，但必须给出更好的理由**——重试门槛是"理由质量高于上次"，而非固定冷却期。
4. **参会方模型（Q4 引出的前置设计）**：不是全员参加——**申请方提议期望参会者 → 经理审批时可增删**；产出**申请方与经理各一份结论**，**经理可决定抄送给哪些其他子 Agent**（抄送进入被抄送方可见消息，是否写入其任务上下文由经理策略决定）。
5. **并发：经理批量处理 + 同类可合并**——多个子 Agent 同时申请时，经理一次审一批，同类主题可并成一个会。
6. **边界：会议申请是横向交流的补充**——横向交流（点对点）解决不了的问题才申请集体会议；无硬性界限，由子 Agent 判断 + 经理把关。
7. **预算：申请时指定来源**——子 Agent 声明用任务配额还是全局预算，经理审批时确认。

## 10. 圆桌三问决议（2026-08-24，M1 定稿依据）

（评审记录：logs/V2协作引擎M1三问评审...md）

### 10.1 审计粒度底线 → L2（输入快照 + 输出摘要 + token 消耗）

- 五位专家全票选 L2；**L3（推理路径追踪）判定为"伪精确"**（LLM 非确定性解码下记录的是采样轨迹而非推理本身），不采用；L4（产出物哈希）对文本价值有限，M2+ 再评。
- **M1 补最低摘要可信性约束**：token 消耗由状态机自动核验（客观字段）；输出摘要须含可被硬规则校验的结构化字段（引用的输入快照 ID、关键决策点枚举），不靠自由文本。

### 10.2 质量裁决权 → 硬规则 → 经理"暂定" → 圆桌申诉

- "终审"软化为"**暂定**"（终审的"终"字是暴力；质量是协商性的，不是判定的）；终审权绝对化必然"唯上是从"。
- 申诉 = **例外通道**（受理条件：产出被下游引用后发现问题 / 硬规则与经理判断冲突），不设常态申诉；"暂定"设时效窗口防悬而不决。

### 10.3 横向交流底线 → 引用锚点 + 指名回应（拉模式）

- **验收标准（全票采纳）**：B 能否仅凭 A 的引用锚点 + 输出摘要做出决策，而不回溯 A 的完整上下文。
- 接受"可发现（拉）优于被推送（推）"；M1 补**最低提醒机制**（状态机事件通知"某产出可用"，非内容推送），防信息复用靠偶然。
- 历史学家补充：M1 需保证"**可追问**"（收信方有权追问信源）。

### 10.4 贯穿性设计（成本与逻辑自洽）

- **三问共享同一份"产出记录"**：审计记录什么 → 裁决依据什么 → 交流引用什么，**单一事实源**；若各用各的记录，M1 将产生三套不一致事实源。

### 10.5 其余风险（既有）

- 记忆污染（陈旧事实扩散）→ FR9 治理机制兜底。
- Manager 成为瓶颈/幻觉放大器 → 硬编码规则兜底 + 只裁决不发明事实。
- 横向交流被滥用（刷屏/串通）→ 配额 + 授权集合限制。
- 任务间执行依赖（A 完成后触发 B）→ M1 否决，M2 评估。

### 10.6 M2 评审项（元问题）

- **"协作本质是否预设了底线"**：圆桌建议 M2 再评，避免 M1 的务实选择（L2 审计 + 暂定裁决 + 拉模式交流）悄悄成为"协作被稀释"的默认前提。V2 与 V1 的本质区别应是"状态机让协作责任可追溯、可纠错、可追问"，而非"多了一个状态机"。

## 11. 圆桌评审决议（2026-08-24）

1. **M1 核心 = 异步任务状态机**（全票）：状态机是模式 B 区别于 V1 的"执行层契约"；横向交流与记忆是"内容层"优化。
2. **状态机必须绑定产出可审计性**：pending→done 记录输入快照、输出摘要、token 消耗（M1 至少到"输出摘要+token"粒度；推理路径追踪、产出物哈希列为 M2+ 审计增强，防 1.5 周周期失守）。
3. **M1 范围收敛**：横向交流 = 最简指名回应（reply_to 指针，授权集合硬编码）；记忆分区后置 M2；任务间执行依赖否决（DAG 复杂度翻倍）。
4. ~~遗留三个开放问题~~ → **已由圆桌三问决议解决（见 §10）**：审计粒度 L2（含摘要可信性约束）、裁决权分层（硬规则→经理暂定→圆桌申诉）、横向交流底线（引用锚点+指名回应+验收判据）。
